# Preliminary research on the `.crp` format

Status as of 2026-10-11. These notes are based on the game DLLs and samples in `data/maps/`. They record current observations, not a complete implementation specification.

`TransferManagerData` now decodes the reader's versioned amount arrays, raw 16-per-reason counts, and offer columns from inner version 37; `SimulationManagerData` bounds it between the TransferManager and NaturalResourceManager profiler tags. `TransferManagerEditor` edits fixed-size arrays and existing offer slots while preserving every unchanged column byte-for-byte. Manager replacement can resize the body and retains the following graph bytes. The editor does not add or remove offers, resolve the closing profiler reference, or name individual count categories. Decoding is capped at one million offers to bound allocations from untrusted count arrays.

`NaturalResourceManagerData` decodes the reader's versioned grid and area-resource columns and preserves the complete bounded body for exact unchanged writing, including the pre-version-22 columns discarded by the game reader. Its direct ore, oil, sand, water, shore, pollution, burned, and destroyed grids can be edited by cell; pre-version-22 ore/oil edits must retain the zero/nonzero masks used by the legacy columns. Forest values can be edited while retaining the zero/nonzero selection for sparse tree and fertility arrays, and those sparse values can be edited by their selected cell. The eight used-resource counters from version 116 and two pollution-disposal rates from version 147 can be edited at their existing offsets. The ten possible area-resource arrays can be edited by positional array and cell indexes; their resource names remain unknown to this API. Editing any of them canonically rewrites the complete shared UInt-array scope. Changed grids or area-resource arrays can resize the manager body while retaining other source bytes.

`ImmaterialResourceManagerData` decodes the versioned local resource grids and five aggregate arrays. Setters edit local final and temporary values by cell and versioned resource-slot index, plus the serialized aggregate prefixes at their documented gates. Changed local arrays are re-encoded and can resize the manager body; unchanged arrays and other source bytes are retained. `SimulationManagerData::replace_immaterial_resource_manager_data` checks the source body and adjacent ElectricityManager boundary after replacement.

`ElectricityManagerData` decodes the conductivity plane, sparse conductive-cell fields, pulse records, versioned node-group array, and scalar tail. It can edit conductivity and all sparse values of an existing cell, insert or remove conductive cells with explicit values for every sparse column, edit existing pulse records, and edit node-group values where serialized. Versions 8–75 retain the raw temporary-electrification byte, and version 75 also retains its otherwise-unmodeled UShort column. Changed encoded arrays use the canonical writer; unchanged fields retain their source bytes. `SimulationManagerData::replace_electricity_manager_data` checks the source body and WaterManager boundary and preserves following manager bytes when the body changes length.

`WaterManagerData` decodes the versioned water, sewage, and heating grids, pulse records, node arrays, and unresolved guide headers. `SimulationManagerData::decode_water_manager_data` bounds the body between WaterManager and ZoneManager. Its processed-cell count, conductive-cell count, continuation flag, conductivity-plane values, insertion/removal of water and version-227 heating conductive cells with explicit sparse-field values, existing water, sewage, and heating pulse records, existing sparse electrification flags and conductive pollution values, sparse water and sewage pressures and version-227 heating pressures and pulse-group indexes, the closest-pipe segment grid from version 73 and closest-heating segment grid from version 227, water and sewage node pulse-group indexes and current and extra pressures, version-227 heating node pulse-group indexes and current and extra pressures, the node-pollution grid from version 23, version-270 collect-water Bool selectors, and collect-pressure grids from inner versions 271 and 272 can be edited. `SimulationManagerData::replace_water_manager_data` checks the bounded source body and ZoneManager boundary; re-encoding changed arrays can change the WaterManager body length while preserving the remaining manager bytes.

## Rust implementation status

The crate has an outer-container reader and compact writer. `Package::read_from` reads package versions 4–10 using the base implementation's zero data offset; `Package::read_from_with_data_offset` accepts an implementation-specific offset. The reader retains index order, checksum strings, unknown numeric asset types, and raw payload bytes, and rejects payloads whose MD5 does not match the index. `Package::write_compact_to` emits assets in index order with recalculated contiguous offsets and MD5 checksums. It preserves the stored author field without decrypting or encrypting it. Type-53 payloads can be parsed as bounded nested packages with `Asset::read_nested_package`; this path has synthetic fixture coverage but no game-produced nested-package validation.

`MapMetaData::decode` and `encode` support the 25-field reflected type-100 `MapMetaData` schema, including mod entries and trailing bytes. `SystemMapMetaData` supports outer types 102 and the observed 107/runtime mismatch, preserving the outer type and unknown suffix; `DistrictStyleMetaData` supports the type-105 schema, including null versus empty string arrays. Other reflected metadata runtime types remain raw. `TextureAsset::decode` and `encode` support type-3 image wrappers, including the outer-version-6 anisotropic-level gate. Image bytes remain opaque and are preserved. `SimulationMetaData::decode_from` and `encode` handle the first type-52 DataSerializer root and return its consumed length. `SimulationManagerData::decode` and `encode` handle the second root's scalar fields, fixed build-index history, manager reference array, and mod serializable-data storage; the GameArea, Terrain, Water, Weather, InstanceManager, PathManager, PropManager, and standalone ZoneManager body prefixes and the NetManager lane, node-flag, node-problem, node-counter, node-record, segment-flag, segment-problem, segment traffic-light, segment coverage, standalone `GuideTriggerBase` prefix, `NetNodeInstanceGuide` body, and shared `GuideInstanceBody` schemas can be decoded. `GuideManagerReferences` decodes its version-gated reference headers and preserves its original body bytes for exact rewriting. `UnlockManagerReferences` decodes version-gated milestone arrays and retains unresolved references; `locate_unlock_manager_unused_guide_bodies` resolves the two version-gated unused-guide bodies where the preceding queue is understood. `MessageManagerData` decodes the two object arrays, version-gated message metadata, timer bytes, and raw profiler index; `MessageManagerDataEditor` edits the recent-message index, per-message last-created frames, last random-message frame, and stored timer bytes without changing queue references or body length. `AudioManagerEditor` edits fixed-width playback fields for existing radio channels and cooldowns for active content while preserving prefab scopes and object references. `SimulationManagerData::decode_message_manager_data` checks the boundary against `GuideManager`, and `replace_message_manager_data` validates the source bytes and preserves the graph length; AudioManager replacement applies the same source and adjacent-boundary checks. BuildingManager prefixes through monument-effect, faculty-bonus, and race-team prefab-reference tables can be decoded and edited with paired assignment/reference writers. Original queued bytes remain available for exact rewriting; `WaterSimulationEditor` supports explicit Water edits, and `InstanceManagerEditor` supports name edits while retaining group references. `PathManagerEditor` edits existing active units' path-find flags, lane-type flags, and version-sized vehicle-type masks; in versions that serialize speed, it also edits the speed byte. `replace_path_manager_data` validates the source body and NetManager boundary and preserves graph length. Path-unit links, positions, counts, and all other bytes remain unchanged. `PropManagerEditor` edits existing active-prop prefab indexes, positions, and angles while preserving flags and name scopes. `locate_net_manager_guide_body`, `locate_building_manager_guide_body`, `locate_water_manager_guide_bodies`, and `locate_zone_manager_guide_bodies` resolve their respective headers to queued offsets when all preceding queued types are among the supported manager-reference schemas. `resolve_transport_manager_references` resolves TransportManager milestone and tail object IDs and types through inner version 115999. `decode_transport_manager_line_data` decodes the shared line-number table, active-line fields, and global passenger records while preserving their original section bytes; its paired editor edits version-gated active-line scalar fields, legacy per-line vehicle selections from versions 112004–114000, shared line numbers, and per-line and global passenger counters while preserving the bounded manager body length. Legacy selection names must retain the original compact or wide encoding and serialized length. It validates the enclosing manager boundary; object headers and the transport-selection table remain in their dedicated APIs. The supplied corpus has no active lines or nonempty milestone list, so these fields have synthetic expected-byte coverage only. `decode_transport_manager_selection_prefix` decodes the version-114001 selection keys and shared strings, resolves existing indexes against the preceding manager profiler tags and BuildingManager selection tables, and retains the original field bytes. `TransportManagerSelectionEditor` edits existing signed 16-bit keys, values declared by new shared strings, and existing indexes that point to a string already available at that entry. New-string edits preserve the source encoding and width and affect later references to that shared-string index; redirecting an existing index changes only that entry. `replace_transport_manager_selection_prefix` checks the source table, version, and enclosing manager boundary before patching fixed-width fields in place. It does not add or remove entries or rewrite an existing shared-string value. Synthetic tests verify exact expected bytes and unchanged graph length. `resolve_economy_manager_references` handles the two base guide references through version 115999; for newer versions it locates exactly two or five newly declared `GenericGuide` references in the bounded EconomyManager body, but does not yet resolve null or existing-object headers in those fields. `decode_economy_manager_investment_flags` reads the 254 activity flags; `decode_economy_manager_investment_value_series` decodes active float histories; `decode_economy_manager_investments` adds the modeled numeric columns; and `decode_economy_manager_investment_prefabs` decodes version-gated investment flags, histories, numeric columns, and prefab assignments/names from inner version 116009 onward when the bounded body matches a supported layout and its guide headers are new declarations. The WaterManager locator supports two null or three-byte object headers in its tail. NetManager guide editors support `NetNodeInstanceGuide`, `NetSegmentInstanceGuide`, and the three 11-byte base-only guide classes; BuildingManager editors support 17-byte building-instance/fire-guide and 11-byte base-only guide bodies; ZoneManager locating supports the 11-byte `ZoneTypeGuide` and `GenericGuide` layouts. ## Confirmed file prefix

The sample `data/maps/CL Wolf Creek.crp` begins as follows:

```text
offset  size     observation
0x00    4        ASCII `CRAP`
0x04    2        little-endian u16 = 6
0x06    1+N      7-bit length prefix, followed by the name `CL Wolf Creek`
```

For this name, the length prefix at byte `0x06` is `0x0d` (13 bytes). This encoding matches .NET `BinaryWriter.Write(string)`. The same kind of prefix appears for map names of different lengths; for example, `AP Asanu Beach` starts with `0x0e`.

Additional fields and text-readable names or identifiers follow the package name. Their container layout is now confirmed from IL below. Strings in the sample include `Wolf Creek_SteamPreview`, `Wolf Creek_Snapshot`, and `Wolf Creek_Data`; .NET type names and PNG data also appear later. These strings should not yet be treated as a complete entry listing, or as proof that every file contains the same set of entries.

## Container index confirmed from IL

The IL for `ColossalFramework.Packaging.Package.ReadIndexTable` was decoded. It confirms this read order:

```text
char[4]  package ID (`CRAP`)
u16      package format version
string   package name
string   package author
u32      package version
string   main asset name
i32      asset count
i64      base data offset
```

Each index record is then read as:

```text
string   asset name
string   asset checksum
i32      asset type
i64      asset offset, relative to the package data area
i64      asset size
```

For each entry the reader computes its stream offset as the record's relative offset plus the base data offset plus `PackageImplementation.dataOffset`. The base `PackageImplementation` returns zero for `dataOffset`; a packaged implementation has a separate override. The read size is converted to `i32` when the in-memory asset is constructed, despite being stored as `i64` in the index.

The concrete implementations clarify that offset rule. `FilePackage.GetStream` opens the package file and `MemoryPackage.GetStream` wraps the package byte array; both use the base zero `dataOffset`. For nested packages, `PackagedPackage.GetStream` delegates to its containing `Asset.GetStream`, and its `dataOffset` is the containing asset's absolute offset in the parent package. The nested index's relative payload offsets are therefore added to that parent offset. The inspected `Asset.GetStream` path does not bound nested reads to the containing asset's declared size. No type-53 package entry appears in the map corpus; the nested-package behavior is DLL-derived and has no map-sample validation.

The record's second string is passed to the `Asset` constructor as its checksum. The sample uses 32-character lowercase hexadecimal MD5 values; the algorithm and corpus-wide match are confirmed below.

This layout matches `CL Wolf Creek.crp` exactly. Its header values are version `6`, package name `CL Wolf Creek`, empty author, package version `0`, main asset `CL Wolf Creek`, four records, and base data offset `337` (`0x151`). The four records are:

| Asset name | Type value | Relative offset | Size |
| --- | ---: | ---: | ---: |
| `Wolf Creek_SteamPreview` | 3 | 0 | 286,048 |
| `Wolf Creek_Snapshot` | 3 | 286,048 | 102,218 |
| `Wolf Creek_Data` | 52 | 388,266 | 4,215,002 |
| `CL Wolf Creek` | 100 | 4,603,268 | 2,908 |

The index ends at offset `0x151`, matching the base data offset. The final entry ends exactly at the file size (4,606,513 bytes).

## Writer corroboration and asset types

`Package.Save` in `ColossalManaged.dll` writes the same header and index fields in the same order as `ReadIndexTable`. It writes asset payloads after the index, copying from a disk path, in-memory byte array, or an existing asset stream. For a non-empty package author it encrypts the author string with `SimpleAES`; an empty author is written as-is. A reader should expect the author string to be empty/plaintext or encrypted, depending on the file.

Before writing the index, `CalculateDataStartOffset` computes the payload start from the stream's current position, adds eight bytes for the base-offset field, then adds each record's encoded name and checksum string lengths plus 4 bytes for type, 8 for relative offset, and 8 for size. ### Type-53 nested package entries

`Package.ReadIndexTable` (ColossalManaged.dll RVA `0x3C784`, IL `0x0180`–`0x019C`) checks each newly indexed asset's type. For type `Package` (numeric 53), it constructs another `Package` using the entry name and `Asset`; that constructor creates a `PackagedPackage` implementation (RVA `0x3BC80`) and reads an inner index. `PackagedPackage.GetStream` / `get_dataOffset` (RVAs `0x3D190` / `0x3D1C1`) use the parent asset stream and its absolute offset. `Package+Asset.GetStream` (RVA `0x5CC80`) seeks the containing package stream to the asset offset but returns that shared stream without limiting reads to the asset's declared size. As a result, malformed nested offsets can cross the parent entry's range while remaining inside the parent package file; the supplied DLL does not enforce the parent asset boundary on this path.

This confirms that the framework treats a type-53 payload as another package and opens it recursively. The inspected `Package.Save` path copies each asset's bytes as provided; it does not flatten nested entries into the parent index. Across the 105 local maps and 469 indexed assets, there are no type-53 entries, so the nested header layout, real-world depth, and intended range constraints remain unverified against a game-produced nested package. The Rust reader should bound child parsing to the containing asset's exact byte range even though the inspected game path does not.

`Asset::read_nested_package` now accepts only type 53 and runs the existing package reader over a cursor restricted to the asset payload. A synthetic version-6 child package confirms successful parsing; a truncated child followed by another parent asset confirms the child reader cannot consume bytes beyond its payload. This implementation follows the recursive type-53 path in `Package.ReadIndexTable` (ColossalManaged.dll RVA `0x3C784`) and the parent-relative offset behavior of `PackagedPackage` (RVA `0x3BC80`). The local map corpus contains no type-53 entry, so the nested path and its version-4–10 support have no game-produced sample validation.

The decoded reader layout was applied to all 105 map files. Every index parsed, every index ended at its declared base data offset, and every asset range fit within its file. This confirms the shared container layout across the observed format versions 4–10; it does not yet prove that all other `.crp` package families use the same implementation or payload encoding.

`Package.ReadIndexTable` (ColossalManaged.dll RVA `0x3C784`) has one package-format-version-specific index behavior: when the header's `u16` format version is 2, it remaps legacy asset type values 5–8 to `Text`, `Assembly`, `Data`, and `Package` (current values 50–53) through `RemapAssetType` (RVA `0x3C73C`). The later `u32` package version is not used for this remapping. The index field order and widths have no other version branches in this method; all observed versions 4–10 use the same layout. The version-2 remapping is DLL-confirmed but outside the map corpus.

## Reflected metadata payloads

The type `100` main asset in `CL Wolf Creek.crp` uses the framework's reflected object serializer. Its header is `bool isNull`, assembly-qualified runtime type string, object-name string, and little-endian `i32` field count. In this sample the values are `false`, `MapMetaData, Assembly-CSharp, ...`, `CL Wolf Creek`, and `25`.

Each reflected field begins with a null marker. A non-null field then stores its runtime type name and field name as .NET `BinaryWriter` strings, followed by its value. Null fields store only the marker; their identity comes from the reflected field order. Arrays store a little-endian `i32` length and then each item. DateTime values are round-trip strings (`DateTime.ToString("O")`). `PackageWriter.WriteUnityType` handles supported Unity/framework types and `PackageDeserializer.DeserializeObject` reads the corresponding field records.

The 25 `MapMetaData` fields in `CL Wolf Creek` were parsed to the end of the 2,908-byte entry. Values include `builtin=true`, `environment="North"`, `mapThemeRef=null`, `mapName="Wolf Creek"`, timestamp `2019-01-30T13:02:49.7692598+02:00`, image and preview checksums `1419a823a786f548fac710b6bde981b5` and `f52b6e1764cf54d1ed79295494e8ed0f`, `mods=[]`, and the inherited `assetRef` checksum `3bb3661184961300c39107046eea3e0d` (the `_Data` entry). Remaining fields are the published hash, buildable area, resource quantities, and route counts.

The implemented type-100 codec handles this field order: `builtin` (Boolean), `environment` (String), `mapThemeRef` (String), `mapName` (String), `timeStamp` (DateTime round-trip string), `imageRef` and `steamPreviewRef` (asset references), `publishedHash` and `buildableArea` (`i32`), `maxResourceAmount` (`f32`), five resource amounts (`u32`), eight route counts (`i32`), `mods` (`ModInfo[]`), and inherited `assetRef` (asset reference). An asset reference's serialized value is its checksum string. `mods` is an `i32` count followed by each mod name as a BinaryWriter string and its workshop ID as an unsigned little-endian `u64`. `Assembly-CSharp.dll` `PackageHelper.CustomSerialize` (RVA `0x65A8`, IL `0x0507`–`0x053A`) writes `ModInfo.modName` and then `ModInfo.modWorkshopID`; `PackageHelper.CustomDeserialize` (RVA `0x7A28`, IL `0x0423`–`0x045C`) reads a string and then `ReadUInt64`. `MapMetaData.mods` references an array of this struct. The committed version-4 sample's `UnlimitedMoney` entry stores eight `0xFF` bytes, which the unsigned codec preserves as `u64::MAX` (the previous signed API displayed the same bits as `-1`). Null fields retain their position in the 25-field layout and store only the null marker. Some version-4 metadata payloads have zero padding after the final field; the codec preserves trailing bytes so decode/encode reproduces those payloads exactly.

`Assembly-CSharp.dll` field metadata declares `MapMetaData.mapThemeRef` as `System.String` (field signature `0x06 0x0E`), unlike the neighboring image fields, which are `Package+Asset`. All 104 type-100 payloads in the local corpus have this field null, so corpus round-trips could not expose a wrong non-null wire type. The Rust codec now uses `System.String` when encoding a newly populated value; a regression test inspects the emitted field header independently. The meaning of a non-null map-theme reference remains unverified against a game-produced sample and is preserved as an opaque string.

`PackageDeserializer.DeserializeObject` (ColossalManaged.dll RVA `0x40A04`) reads each non-null field according to the runtime field type. All five type-102 and twelve type-105 entries in the 105-map corpus are in `CO.crp` (outer format version 10). The five type-102 records have four fields and parse exactly to their payload ends (681–687 bytes). ### Reflected serializer behavior and unknown fields

`PackageSerializer.Serialize` (ColossalManaged.dll RVA `0x3FE1C`) obtains instance fields through reflection, filters them with `PackageSerializer.IsSerializable` (RVA `0x3FD04`), writes the selected field count, and serializes each field header and value. The filter excludes `[NonSerialized]` fields; fields must be public or carry the framework's `UIDropDown` attribute, and their type must be a Unity type or CLR-serializable (arrays are checked by element type). `AssetSerializer.SerializeHeader` (RVA `0x3B638`) writes a Boolean null marker for every selected field; null values keep their position in the count and have no following type, name, or value. No package-version branch appears in this generic reflected-object writer.

On read, `PackageDeserializer.DeserializeObject` (RVA `0x40A04`) looks up each serialized field name on the runtime type and calls `ResolveLegacyMember` (RVA `0x40334`) if that name is absent. If no field matches, the reader still decodes the value from the serialized runtime type, but skips assignment, so a subsequent object-level write cannot reproduce that unknown member. For an unknown runtime type, `AssetSerializer.DeserializeHeader` (RVA `0x3B6C4`) first tries normal and legacy type resolution, then calls the configured unknown-type handler. `AssetSerializer.HandleUnknownType` (RVA `0x3B6A0`) can skip the value only when that handler returns a positive byte count; otherwise deserialization throws `InvalidDataException`. The framework therefore offers no general length-based skip for arbitrary unknown values. Keeping the original reflected payload bytes is necessary for a lossless read/write path across schema changes.

Type-3 texture entries use a dedicated texture reader rather than the generic reflected field-count form. The entry stores the non-null marker and runtime type string, then the texture name, a `linear` boolean, an `i32 anisoLevel` for outer package versions 6 and newer (older versions default it to 1), an `i32` byte count, and that many image bytes. The `CL Wolf Creek` textures have `linear=false`, `anisoLevel=1`, and PNG image data. This sequence was checked across all 237 type-3 entries: every byte count exactly matches the remaining payload, and every image buffer starts with the PNG signature `89 50 4E 47 0D 0A 1A 0A`.

The Rust type-3 codec preserves the assembly-qualified runtime type and image bytes. Its encode/decode path was round-tripped against all 237 type-3 payloads in the external 105-map corpus, including the pre-version-6 `anisoLevel` gate.

## Type-52 map data payloads

The type-52 data payload does not use this reflected header. IL inspection traces its source: `LoadingManager.SaveSimulationData` writes a temporary file by calling `DataSerializer.Serialize` first for `m_metaData`, then for a new `SimulationManager+Data` object. The map packaging callback adds this file as the `_Data` entry with type `Data` (52). Each call writes a 32-bit format version before its root object, so the payload contains two sequential DataSerializer streams.

Each DataSerializer stream starts with a big-endian `u32` format version. `DataSerializer.WriteUInt32` emits bytes most-significant first, and `Deserialize` reads two big-endian `u16` values to recover its version. This differs from the little-endian package header/index. The beginning of `CL Wolf Creek_Data` is `00 01 B5 84` (`0x0001B584`); `ND Island Hopping_Data` begins `00 00 01 3C` (`0x0000013C`).

The internal DataSerializer versions vary independently of the outer package version. Across the corpus, the ranges are: package v4, `0xF4`–`0x140` (5 distinct values); v5, `0x1A9CE` (1); v6, `0x1A9D3`–`0x1B96F` (7); v7, `0x1B972` (1); v8, `0x1BD57`–`0x1C14F` (6); v9, `0x1C52A`–`0x1C534` (4); and v10, `0xC2`–`0x1CCFB` (5). A reader must track these two version fields separately. The object framing and selected manager schemas are recovered below; most manager-specific payload fields remain to be mapped.

`DataSerializer` also uses its own primitive encoding, distinct from both the package header and .NET `BinaryWriter` strings. IL confirms that `WriteUInt16` and `WriteUInt32` emit most-significant bytes first. `WriteUniqueString` writes `0xFF` for null; otherwise it writes a big-endian 24-bit character count. If every character fits in one byte, bit `0x800000` marks the count and each character is delta-encoded from an initial value of 128 into one byte. Strings containing wider characters use unflagged length and big-endian 16-bit deltas.

Object framing from `WriteObject` and `WriteSharedType` is:

- `0xFF` represents a null object.
- A previously encountered object is represented by its object-list index as a big-endian 24-bit integer. The writer limits these IDs to values below `0xFE0000`, keeping them distinct from the `0xFE` new-object marker.
- A new object begins with `0xFE`, followed by its shared-type reference. Existing shared types use a big-endian `u16` type-list index. A new shared type is encoded as `0xFE` followed by a `WriteUniqueString` assembly-qualified type name.
- New objects are added to an object list and later serialized in that list's order through `IDataContainer.Serialize`. This preserves references and allows the root object's serialization to enqueue further objects.

`DataSerializer.Serialize` and `Deserialize` in ColossalManaged.dll (RVA `0x4881C`, `0x488C3` / `0x488D0`) confirm that the queue is dynamic. Serialization walks `m_objectList` by increasing index and rechecks its count after each object's `Serialize`, so objects referenced by a queued body are appended and written later in the same stream. Deserialization first reads the root through its delegate, then walks the growing list and calls each object's `Deserialize`; after that pass it walks the final list again and calls `AfterDeserialize`. Thus an object's body boundary depends on its complete `Deserialize` implementation and any objects it enqueues. Knowing the standalone `NetNodeInstanceGuide` schema is not enough to locate its body in the full stream; earlier queued bodies must also be parsed in queue order.

`WriteObject` / `ReadObject` (RVAs `0x47CA0` / `0x47D54`) assign a new object's ID from the current `m_objectList.Count`; an existing reference reuses that 24-bit ID. The manager-reference array declares all root managers before their queued bodies are serialized. Nested objects declared while each manager body is serialized are appended to the list in manager order. While the later nested-object pass is running, any further child references append after objects already in the queue. For GuideManager, all 36–58 reader-present references in each local sample are new declarations, so they reserve a consecutive ID block while its manager body is read. Their serialized bodies are not guaranteed to form the stream suffix: earlier queued objects can append additional children after that block. Locating GuideManager's own referenced bodies therefore still requires parsing all preceding queued objects. The new BuildingManager locator handles the narrower queue prefix by decoding the earlier GameArea, Terrain, InstanceManager, and NetManager references and advancing across recognized guide-body schemas; other earlier child types cause it to return an unsupported-type error.

The first bytes of `CL Wolf Creek_Data` after its `u32` version are `FE FE 80 ...`. This matches a new root object, a new shared type, and the flagged compact-string form. Decoding that string yields `SimulationMetaData, Assembly-CSharp, Version=0.0.0.0, Culture=neutral, PublicKeyToken=null`. The next fields also match `SimulationMetaData.Serialize`: the game-instance identifier is `7a8bf7ba-d1dc-45ed-b96b-93e75f9c7130`, the environment is `North`, and the scenario asset/name are null. Continuing with the field sequence from IL parses the complete metadata object through byte 192. A second big-endian version word `0x0001B584` begins at payload offset 193, immediately followed by another `FE FE 80 ...` object/type header. This identifies the boundary between the two Serialize calls in this sample and confirms the second call uses the same version. Its root type is `SimulationManager+Data, Assembly-CSharp, Version=0.0.0.0, Culture=neutral, PublicKeyToken=null`.

### PathManager body and NetManager boundary

`PathManager+Data.Serialize` / `Deserialize` in Assembly-CSharp.dll (RVA `0x2D5284` / `0x2D542C`) start with path-unit simulation flags for buffer indices 1 onward. `PathManager.Awake` (RVA `0x2D3E64`) allocates 262,144 path units, so the current buffer has 262,143 serialized flags. ### NetManager node problems

Immediately after the node flags, `NetManager+Data.Deserialize` (Assembly-CSharp.dll RVA `0x2A4C80`) reads problem bits only for nodes whose primary `m_flags` is nonzero. Inner versions 115000 and newer use two `EncodedArray.ULong` values per active node. Versions 221–114999 use one ULong if the saved application version is at least `BuildConfig.MakeVersionNumber(1, 3, 0, 1, 1, 0)`, or 146809088. Earlier applications and inner versions use one `EncodedArray.UInt` value. `BuildConfig.MakeVersionNumber` (RVA `0x34DB`) packs its six components into a `u32`; the Rust API takes `SimulationMetaData.save_app_version` explicitly and rejects a missing value when this gate matters. The legacy UInt reader moves bits 30–31 to bits 62–63 before constructing `Notification.ProblemStruct`; its constructor (RVA `0x2D88D8`) sets the second 64-bit field to zero.

`EncodedArray.ULong.Read` in ColossalManaged.dll (RVA `0x5EFF0`) uses the same control ranges as the UInt codec, but full literals are big-endian `u64` and close-delta adjustments are signed big-endian `i32`. The Rust decoder preserves the original problem-array bytes for exact rewriting and stops before later node counters and records. It decoded the problem-array gate in all 110 local type-52 assets; 175 nodes have nonzero problem bits. In `CCMP2 Desert Map 1` (inner version 116020), 2,082 active nodes yield a 33-byte zero-valued paired ULong stream. In `CL Wolf Creek` (inner version 112004, saved application version 184558064), 1,551 active nodes yield a 39-byte single-ULong stream; nodes 15865 and 27884 each have problem value 4096. For `Byte`, control `0x00`–`0x7F` means the next `control+1` bytes are literal values. Control `0x80`–`0xFF` repeats the previous signed byte delta `control-0x7F` times; each result is previous value plus that delta modulo 256.

The Water editor currently emits only `0x00`–`0x3F` literal controls (up to 64 values) and `0x80`–`0xFF` repeated-delta controls (up to 128 values). This is a documented canonical encoding choice; it is not a claim to reproduce the DLL writer's byte-for-byte run grouping. The same bit-level codec is used for signed `Short` velocities, interpreted as two's-complement `i16` values. Synthetic expected-byte tests cover literal and repeated-delta controls, signed velocities, sparse-mask boundaries, source and wave records, wave preservation, and an edited type-52 asset written through the package writer. The opt-in local corpus test also decodes canonically re-encoded Water bodies and compares every grid and source field across the available maps.

For `UShort`, control `0x00`–`0x3F` means the next `control+1` big-endian `u16` values are literals. Control `0x40`–`0x7F` means `control-0x3F` signed-byte adjustments to the previous delta; each adjusted delta is added to the previous value. Control `0x80`–`0xFF` repeats the previous signed 16-bit delta `control-0x7F` times. Reconstructed values wrap to 16 bits. Both codecs initialize the previous value and delta to zero. The DLL defines corresponding encoded-array helpers for signed/unsigned integers, floats, booleans, and 64-bit values; their exact codecs have not been analyzed here.

## Findings from the DLLs

1. The format is a package container rather than a single raw map image: the libraries include dedicated package readers and writers, an index table, and a collection of entries.
2. The container has a versioned header and an index layout confirmed above. The supplied corpus contains multiple versions, so a Rust reader should preserve and explicitly validate the version number.
3. `Package.Save` copies asset payload bytes into the package; no generic compression layer was found in the container writer. Type-3 assets contain PNGs, and specific DataSerializer array fields use delta/RLE encoding; other fields may have their own encodings.
4. Entry checksums are lowercase hexadecimal MD5 hashes of the raw asset payload. `SecurityHelper.CalculateChecksum` computes MD5 and formats it as lowercase hex; the `Package.Asset` constructors call the byte-array or file overload. Recomputing hashes for all 469 entries across the 105 supplied maps matched every stored checksum.
5. The code separates container handling (reader, writer, index, entries) from game-object serialization (`PackageSerializer`, `DataSerializer`). The type `100` metadata uses the reflected-object path; type `52` uses `DataSerializer` object framing, while the game-specific `IDataContainer` payloads remain to be mapped.
